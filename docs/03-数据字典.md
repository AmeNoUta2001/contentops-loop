# 数据字典

## 快照文件 `reports/tt_snapshots/YYYY-MM-DD.json`

每天一条，是整套分析的事实底座。**只存事实，不存结论。**

```jsonc
{
  "date": "2026-01-13",
  "articles": [
    {
      "item_id": "900000000000000001",   // 平台内容 ID（本仓库示例用 9 开头合成号段）
      "title": "……",
      "item_status": 20,                 // 20 = 已发布（脚本只统计这个状态）
      "publish_time": 1767658800,        // 秒级时间戳；发布晚于 12:00 → 首日窗口取次日
      "read": 101,                       // 截至本次快照的【累计】阅读
      "show": 2198,                      // 截至本次快照的【累计】展现
      "digg": 3, "comment": 1, "repin": 0,
      "show_date": "2026-01-10",         // 发布日（首日窗口的锚点）
      "ctr_calc": 4.6,                   // 累计 CTR（%）—— 仅存档，不用来判断健康度
      "income": { "income_fen": 5, "share_income_fen": 0 },
      "income_rpm": 0.5,
      "traffic": {                       // 逐日流量（仅最近 N 篇有）—— 首日口径的首选来源
        "daily": [
          { "date": "2026-01-10", "impression": 1481, "read": 92 },
          { "date": "2026-01-11", "impression": 180,  "read": 2 }
        ]
      },
      "property": null,                  // 读者画像（仅最近 N 篇）
      "item_info": {                     // 单篇详情（需 backfill 补）
        "ranking_data": {
          "click_rate_rank": 10,
          "interaction_rate_rank": -1,
          "read_complete_rate_rank": -1,
          "to_fans_rate_rank": -1
        },
        "read_complete_rate": -1,
        "read_duration": -1,
        "click_rate_official": 0.055        // 平台口径点击率（小数）
      }
    }
  ]
}
```

### 读这份数据的三个要点

1. **`show`/`read` 是累计值**，只在两个地方有用：① 作为「首日」的次优来源（发布当日快照）；② 观察长期滴灌曲线。**不要用它算 CTR 来判断好坏。**
2. **`traffic.daily` 才是官方逐日口径**，但它只对最近 N 篇开放（平台上越老的稿子越拿不到）。所以留旧快照非常重要 —— 历史首日数据只能靠当时的快照还原。
3. **快照是"某个时刻的照片"**，不是精确日终值。两次抓取同一篇的数值会不同。**同批分析必须同口径**。

## 首日指标输出 `reports/首日指标.json`

`first_day_metrics.py --json <path>` 产出：

```jsonc
{
  "date": "2026-01-13",                 // 用哪天的快照算的
  "rows": [                             // 每篇一行，新→旧
    { "pub_date": "…", "title": "…", "topic": "养猫日常",
      "first_show": 1481, "first_read": 92, "first_ctr": 6.21,
      "total_show": 2198, "total_read": 101, "total_ctr": 4.6,
      "src": "traffic" }                // 首日数据来自哪：traffic / traffic首条 / 快照YYYY-MM-DD(后续)
  ],
  "pool": [                             // 题材池子表
    { "topic": "养猫日常", "n": 3, "n_stable": 3,
      "med_first_show": 1178, "med_first_show_stable": 1178,
      "med_first_read": 73, "med_first_ctr": 7.05,
      "risk": "" }                      // "" | "单篇" | "含爆款" | "爆款污染"
  ],
  "summary": {
    "n": 13,
    "med5_first_show": 661,  "med30_first_show": 881,
    "med5_first_ctr": 6.35,  "med30_first_ctr": 6.35,
    "pass14_rate": 100.0,                // 近14天 CTR ≥ 过线值的过线率（%）
    "ctr6_count": 13, "n14": 13
  }
}
```

## 题材词典 `scripts/topic_taxonomy.py` + `config/vertical.json`

**词典不在代码里**，在 `config/vertical.json`。分类器只提供机制，词表全是配置。

确定性关键词规则，输出三级：

| 层级 | 含义 | 例（示例垂类：宠物） |
|---|---|---|
| `topic_family` | 题材族（大池子/小池子） | 宠物健康、养猫日常、养狗日常 |
| `motif` | 母题（这个题材下的具体套路） | 半夜折腾、老宠临终照顾 |
| `confidence` | 置信度（按命中词数） | high / low / none + 命中了哪些词 |

输出永远带 `family_kw` / `motif_kw`（命中的原词），所以每条归类都能被人工复核、被一句话改掉。

设计取舍：**用确定性规则而不是模型**。原因是分类结果要可复核、可回溯、可复现 ——
分类错了就是分析错了，而模型分类每次结果可能不一样，也没法"加一个词就修好"。

迭代节奏：发现「像本赛道但没归类」的标题 → 往 `families`/`motifs` 加词 →
重跑入库 → 看分布。个案纠错用 `manual_overrides`（不要为一条个案去污染通用词表）。

| 配置字段 | 谁在用 |
|---|---|
| `families` / `motifs` / `motif_must` | `topic_taxonomy.py`、`first_day_metrics.py`（题材池子表） |
| `off_vertical` | `topic_taxonomy.py`（跨垂类否决） |
| `niche_pos` / `niche_neg` | `benchmark_store.py`（判断一个同行账号在不在同赛道） |
| `niche_hint` / `offlike` | `same_topic_weekly.py`（抽样给人工复核时挑"像本赛道但没归类"的） |
| `thresholds` | 全部脚本（过线值、池子档位、爆款线、最小样本数） |

## 基准库 `reports/benchmark/`

| 文件 | 内容 |
|---|---|
| `accounts.jsonl` | 每账号一行（主页元数据、采集时间） |
| `articles.jsonl` | 每篇文章一行（标题、展现/阅读、发布时间、是否计入分位） |
| `基准快照.md` | 分层分位数 + 我方的分位位置 |
| `手动补录.jsonl` | 人工补录（同 schema） |

**铁律**：只做**同文章年龄桶**内的比较；样本 n < 8 的桶不给分位数。

## 同题库 `reports/same_topic/`

把「同题材对照」入库：每条 = {题材, 标题, 结果(爆/平/败), 母题, 是否自家}。
用途：① 防止幸存者偏差（只记住爆款）；② 看某个母题被反复用过几次（配冷却闸门用）。
